# Graphify and Claude Code skills

## Graphify

**Installation:** already installed as a local CLI (`~/.local/bin/graphify`, plus `graphify-mcp`) and as the Claude Code skill `graphify`. The repository graph `graphify-out/graph.json` (5,129 nodes, code-only AST build per `graphify-out/.graphify_build.json`) existed and is refreshed by the post-commit hook. Nothing was reinstalled, and the graph was not rebuilt from scratch.

**How it informed the codebase work:**

| Query | Finding | Decision |
| --- | --- | --- |
| `graphify query "where are question records stored, canonical question catalog, unit topic assignment"` | Catalog consumers are `components/student-app.tsx` (`topicFor`, `partsForTopic`, filtering) and the review dashboard; catalog builders are `scripts/assemble_catalog.py` and `scripts/build-stage3-catalog.py`; stimulus links run through `lib/question-review-backup.mjs` (`canonicalStimulusLinks`). | Read only those files; confirmed `public/student-questions.json` as the authoritative catalog via `tests/stage3-catalog.test.mjs`. |
| `graphify explain "build-stage3-catalog.py"` | The builder pins catalog blobs by Git hash and merges ledgers; it is the only writer of the catalog. | The concept system never writes to the catalog; concepts live in a separate store keyed by question id. |
| `graphify query "student question bank filtering by topic and type"` | Filtering, sessions and progress all live inside `ChemAtlas()` in `student-app.tsx`. | Concept search is a separate library (`lib/concepts/search.mjs`) with a five-step integration plan, rather than edits to the 800-line component. |
| `graphify affected "topicFor()"` | Only `reviewSession()` depends on it. | Topic logic can stay untouched; concepts add a filter beside it. |
| `graphify path "QuestionReviewDashboard()" "createD1ReviewStore()"` | No direct code path: the dashboard talks to the store through API routes. | The private review service (D1/R2, crop revisions) stays isolated; concept review is a file-based sheet. |

**Impact of this change:** `git diff origin/main` touches only new files plus four lines in `.gitignore`. No existing module imports `lib/concepts/`, so Graphify shows no dependants of the new code in the existing app. The student build and the Worker are unaffected.

**Educational concept graph:** Graphify extracts code structure. It does not classify chemistry, and it has no custom node/edge schema for building educational relationships. It does, however, read any node-link `graph.json` through `--graph`. So the chemistry graph is generated by our own code (`lib/concepts/graph.mjs`) in that format, which makes Graphify's `explain` and `path` work on it:

```text
$ graphify explain "Formal charge" --graph research/concepts/concept-graph.json
  --> Lewis structures [REQUIRES_PRIOR]
  --> Topic 2.5 Lewis Diagrams / 2.6 Resonance and Formal Charge / 2.7 VSEPR and Hybridization [RELEVANT_TO]
  --> Resonance and delocalization, Oxidation numbers [RELATED_TO]
```

Node kinds: unit, topic, concept group, concept, skill, question, FRQ part. Relations: `PART_OF` (topic→unit, part→question), `IN_GROUP`, `RELEVANT_TO` (concept→topic, primary or related), `REQUIRES_PRIOR` (prerequisite), `RELATED_TO`, `BELONGS_TO` (question→topic), `TESTS` (primary concept, with evidence), `REQUIRES` (supporting concept, with evidence). Graphify loads a simple graph and keeps only one edge per node pair, which `graphify diagnose multigraph` confirmed. The generator therefore writes one edge per concept pair, with a prerequisite taking precedence over "related". The authoritative relationships remain in `taxonomy.v1.json` and `classifications.json`; the graph file is rebuilt from them (`cli.mjs build-graph`), so no graph database is needed.
